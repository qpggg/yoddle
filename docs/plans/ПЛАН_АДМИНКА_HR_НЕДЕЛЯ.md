# План: админка для HR (неделя)

**Текущее состояние:** админки в коде нет; пользователи в таблице `enter`, логин через `/api/login`. В бэкапе есть таблица `user_roles` (user_id, role: admin | manager | user).

---

## Этап 1. База (понедельник — первый день)

### 1.1 Роутинг и вход в админку
- [ ] В `App.tsx` добавить роуты `/admin` и `/admin/*` (отдельный layout без Navbar/Footer для сотрудников).
- [ ] Страница `src/pages/admin/AdminLogin.tsx` — форма логин/пароль, запрос к API админ-входа.
- [ ] API: `POST /api/admin/auth` — проверка логина/пароля; если у пользователя роль `admin` (таблица `user_roles`) или логин из списка админов — вернуть успех и токен/флаг сессии.
- [ ] Хранение «админ залогинен»: cookie или localStorage (например `yoddle_admin_session`), проверка при заходе на `/admin/*`.

### 1.2 Обёртка админки
- [ ] Страница `src/pages/admin/AdminLayout.tsx` — боковое меню (или верхнее), область контента, кнопка «Выйти». Показывать только если сессия админа есть, иначе редирект на `/admin`.
- [ ] Роуты внутри админки: `/admin` (редирект на дашборд), `/admin/dashboard`, позже `/admin/employees`, `/admin/benefits` и т.д.

### 1.3 Дашборд HR (минимум)
- [ ] Страница `src/pages/admin/AdminDashboard.tsx` — заголовок «Панель HR», 2–4 карточки: всего пользователей, активных за неделю, потрачено коинов (сумма), количество выбранных льгот.
- [ ] API: `GET /api/admin/stats` — агрегаты по `enter`, `user_balance`, `user_benefits`, `activity_log` (или по тем таблицам, что уже есть). Защита: вызывать только если запрос с валидной админ-сессией.

**Результат дня:** заход на `/admin` → логин → дашборд с базовой статистикой.

---

## Этап 2. Сотрудники и базовая аналитика (второй–третий день)

- [ ] Страница «Сотрудники»: список из `enter` с поиском по имени/email, колонки: имя, email, баланс коинов, кол-во льгот (опционально: последняя активность).
- [ ] API: `GET /api/admin/employees` с query-параметрами поиска и пагинацией.
- [ ] Опционально: один клик по сотруднику — переход к «профилю» (просмотр баланса, льгот, активности) или модалка.

---

## Этап 3. Льготы и коины (четвёртый–пятый день)

- [ ] Админ-просмотр/редактирование каталога льгот: список из `benefits`, добавление/редактирование/деактивация (API уже есть `GET/POST` для benefits — расширить или добавить `PATCH/DELETE` под админа).
- [ ] Управление коинами: начисление коинов выбранному пользователю (или массовое по списку). Использовать существующую логику `admin_add` в кошельке; API: `POST /api/admin/coins` (или расширить wallet API с проверкой админа).

---

## Этап 4. Отчёты и выгрузка (по возможности)

- [ ] Экран «Отчёты»: популярные льготы (топ по количеству выборов), использование коинов по периодам.
- [ ] Кнопка «Выгрузить CSV» по сотрудникам или по транзакциям.

---

## Технические моменты

- **Роли:** если таблицы `user_roles` в актуальной БД нет — добавить миграцию (user_id, role) или колонку `role` в `enter`. Для первого запуска можно захардкодить список админ-логинов в `.env` (например `ADMIN_LOGINS=admin@company.com`).
- **Защита API:** все `/api/admin/*` проверяют наличие валидной админ-сессии (cookie или заголовок с токеном).
- **Стиль:** использовать тот же MUI и тему, что и на основном сайте; админку визуально отличить (другой цвет акцента или боковое меню).

После этапа 1 админка «живая» и можно по шагам добавлять разделы сотрудников, льгот и коинов.
