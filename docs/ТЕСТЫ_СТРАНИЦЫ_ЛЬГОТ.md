# Тесты страницы «Мои льготы» (MyBenefits)

## Охват

- **Страница:** `/my-benefits` (MyBenefits.tsx)
- **API:** `/api/benefits`, `/api/user-benefits`, `/api/wallet/*`
- **Логика:** каталог льгот, выбор до 2 льгот в месяц, списание коинов, возврат в течение 48 ч

---

## 1. Загрузка страницы

| # | Действие | Ожидание |
|---|----------|----------|
| 1.1 | Открыть `/my-benefits` под авторизованным пользователем | Загружаются каталог (`/api/benefits`) и льготы пользователя (`/api/user-benefits?user_id=…`) |
| 1.2 | Проверить блок «Выбранные льготы» | Показываются только льготы текущего пользователя (или «Пока вы ничего не выбрали») |
| 1.3 | Проверить блок «Все доступные льготы» | Список из БД (benefits), у выбранных — кнопка неактивна / «Выбрано» |
| 1.4 | Проверить фильтр по категориям | Чипы «Все» + категории из каталога; выбор фильтрует карточки |
| 1.5 | Проверить рекомендации | Карточки с `id` из `/api/user-recommendations` (или аналог) помечены «Рекомендуем» |

**API для проверки:**
- `GET /api/benefits` → `{ benefits: [{ id, name, description, category, price_coins }] }`
- `GET /api/user-benefits?user_id=X` → `{ benefits: [{ id, name }] }`

## 2. Добавление льготы (покупка)

| # | Действие | Ожидание |
|---|----------|----------|
| 2.1 | Нажать «Купить» на льготе с ценой 0 | Без списания коинов: сразу добавление в «Выбранные», запись в `user_benefits` |
| 2.2 | Нажать «Купить» на льготе с ценой > 0 при достаточном балансе | 1) `POST /api/wallet/purchase` — списание; 2) `POST /api/user-benefits` — добавление; льгота в «Выбранных», баланс уменьшился |
| 2.3 | Нажать «Купить» при недостаточном балансе | Ответ 422 от purchase, сообщение «Недостаточно средств», льгота не добавляется |
| 2.4 | У пользователя уже 2 льготы | Блок «Вы выбрали максимум льгот», кнопки добавления неактивны или скрыты |
| 2.5 | Повторное нажатие на ту же льготу в течение 5 сек | Защита от дубля: второй purchase не списывает коины повторно (handlers.js anti-dup 5 sec) |

**Порядок на фронте:** сначала `POST /api/wallet/purchase`, при успехе — `POST /api/user-benefits`. При падении второго шага коины уже списаны — возможная несогласованность (стоит проверить).

---

## 3. Удаление льготы (без возврата)

| # | Действие | Ожидание |
|---|----------|----------|
| 3.1 | Удалить льготу по кнопке «Убрать» (если есть), когда окно возврата (48 ч) истекло | `DELETE /api/user-benefits` с `user_id`, `benefit_id`; запись из `user_benefits` удалена, в «Выбранных» льготы нет |

*Примечание:* в текущем UI удаление без возврата может быть только через «Убрать» (если кнопка есть), а не через «Вернуть».

---

## 4. Возврат в течение 48 часов

| # | Действие | Ожидание |
|---|----------|----------|
| 4.1 | Добавить льготу за коины, в карточке в «Выбранных» нажать «Вернуть» (в течение 48 ч) | 1) `POST /api/wallet/refund` (body: `user_id`, `transaction_id` или `benefit_id`); 2) при успехе — `POST /api/wallet/refresh`; 3) локально убрать из выбранных; 4) `DELETE /api/user-benefits` — удалить запись; коины вернулись на баланс |
| 4.2 | Вернуть ту же покупку второй раз | Ответ 409 «already refunded», коины не начисляются повторно |
| 4.3 | Вернуть после истечения 48 ч | Ответ 422 «refund window closed», кнопка «Вернуть» неактивна или показывается «Окно возврата истекло» |

**Таймер 48 ч:** фронт считает остаток по `GET /api/wallet/purchases?user_id=&benefit_id=&limit=1` (поле `created_at` последней покупки).

## 5. Баланс и кошелёк

| # | Действие | Ожидание |
|---|----------|----------|
| 5.1 | Открыть страницу Balance или запрос `GET /api/wallet?user_id=X` | Есть баланс (или 0), при покупке он уменьшается, при возврате — увеличивается |
| 5.2 | После покупки проверить `GET /api/wallet/transactions?user_id=X` | Появилась запись типа `benefit_purchase` с нужной суммой и reference_id = benefit_id |
| 5.3 | После возврата проверить транзакции | Появилась запись типа `refund` с той же суммой |

## 6. Граничные и ошибки

| # | Действие | Ожидание |
|---|----------|----------|
| 6.1 | `GET /api/user-benefits` без `user_id` | 400, текст про `user_id required` |
| 6.2 | `POST /api/wallet/purchase` с несуществующим `benefit_id` | 404 «benefit not found» |
| 6.3 | Неавторизованный пользователь заходит на `/my-benefits` | Редирект на логин или пустой список (зависит от роутинга) |
| 6.4 | Каталог пустой (нет записей в `benefits`) | Блок «Все доступные льготы» пустой, без падения |

---

## 7. Что проверить в коде/БД

- **Роуты user-benefits:** в `server.js` обрабатываются GET/POST/DELETE `/api/user-benefits` (inline). Файл `api/user-benefits.js` в сервере не подключается — XP и `activity_log` при добавлении льготы в этом сценарии не начисляются. Если по продукту нужно начислять XP за добавление льготы — либо переназначить роут на handler из `api/user-benefits.js`, либо продублировать логику в server.js.
- **Лимит 2 льготы:** проверяется только на фронте (`MAX_BENEFITS`, `userBenefitIds.length >= MAX_BENEFITS`). На бэкенде при POST user-benefits лимит не проверяется — при прямом вызове API можно добавить больше двух. При необходимости — добавить проверку в API (например, «не больше 2 записей в user_benefits на пользователя за текущий месяц»).
- **Схема кошелька:** при первом запросе к wallet вызывается `ensureWalletSchema()` (таблицы `user_balance`, `coin_transactions`, колонка `benefits.price_coins`). Убедиться, что миграции/скрипты не конфликтуют с этой схемой.

## 8. Чек-лист прогона (кратко)

- [ ] Загрузка каталога и своих льгот
- [ ] Добавление льготы с ценой 0
- [ ] Добавление льготы за коины (достаточно баланса)
- [ ] Отказ при недостатке коинов
- [ ] Блокировка добавления при уже выбранных 2 льготах
- [ ] Возврат в 48 ч: коины вернулись, льгота снята
- [ ] Возврат повторно — 409
- [ ] Возврат после 48 ч — 422
- [ ] Удаление льготы (DELETE user-benefits) без возврата, если есть сценарий
- [ ] Баланс и история транзакций после покупки и возврата

После прохождения этих пунктов страницу льгот можно считать протестированной по текущей логике.
